# Migration 0001 — review before running

**Status: prepared, tested on a throwaway PostgreSQL, NOT executed on Supabase.** Do not run `prisma migrate deploy` (or paste the SQL into Supabase) until the owner approves this document.

- SQL: [`prisma/migrations/0001_init/migration.sql`](../prisma/migrations/0001_init/migration.sql) (≈ 1,000 lines — part 1 generated by Prisma from `schema.prisma`, part 2 hand-written rules and row-level security)
- Behaviour tests: [`prisma/tests/migration-checks.sql`](../prisma/tests/migration-checks.sql) — 60+ assertions, run in CI on every push against a disposable PostgreSQL 16, rolled back afterwards
- The migration inserts **no data**: no products, prices, customers, users or settings (a unit test fails if an `INSERT` is ever added)

## 1. The SQL

It has two parts, in one file, applied in one go:

1. **Part 1 — generated** (`CREATE TYPE`, `CREATE TABLE`, indexes, foreign keys). Prisma produced it from `schema.prisma`; a check confirms the file and the schema agree (`prisma migrate diff` reports "empty").
2. **Part 2 — hand-written** (section numbers match the comments in the file):
   - 2.1 case-insensitive uniqueness for brand / category names and admin e-mails; slug format; E.164 phone numbers; GSTIN shape
   - 2.2 catalogue checks: no negative prices or stock, GST rate 0–100, minimum order quantity ≥ 1. NULL still means "not entered"
   - 2.3 quotation / order / invoice amount and quantity checks; an issued invoice must carry its full GST serial number
   - 2.4 the approval gate: exactly one target, a decision records who/when/as OWNER, hash shape, one open request per target
   - 2.5–2.6 triggers (see below)
   - 2.7 row-level security

## 3. Relationships and delete rules

`Restrict` = refuse to delete the parent while children exist. `Cascade` = delete children with the parent. `Set null` = clear the link.

| Child → parent | On delete |
| --- | --- |
| Product → Category, Product → Brand | **Restrict** |
| Category → parent Category | Set null |
| Lead → AdminUser (assigned), Lead → Customer | Set null |
| Enquiry → Lead | **Restrict** |
| EnquiryItem → Enquiry | Cascade (line items only) |
| Quotation → Customer, Quotation → Enquiry | **Restrict** |
| QuotationItem → Quotation | Cascade (a sent quotation's lines are frozen by trigger) |
| Order → Customer, Order → Quotation | **Restrict** |
| OrderItem → Order | Cascade |
| Invoice → Order, Invoice → Customer | **Restrict** |
| InvoiceItem → Invoice | **Restrict** |
| Payment → Invoice, Payment → AdminUser (recorded by) | **Restrict** |
| FollowUp → Lead, Customer | **Restrict**; → Quotation, Order, AdminUser: Set null |
| ApprovalRequest → Quotation / Order / Invoice / Lead / Customer / AdminUser (decided by) | **Restrict** |
| QuotationItem → ApprovalRequest (price approval) | **Restrict** |
| Line items → Product (all four line tables) | Set null |
| AdminSession → AdminUser | Cascade (deleting a user signs them out) |

All foreign keys use `ON UPDATE CASCADE`. Ids are text (`cuid`), so there are no sequences to expose.

**Database-enforced rules (triggers and checks), each proven by a test:**
- Approved / rejected approvals are **frozen** — payload, hash, expiry, target and approver cannot be edited; `executedAt` can be set once; no deletion.
- Payments, follow-ups, approvals, quotations, orders, invoices and invoice lines **cannot be deleted** (use a status).
- A quotation cannot leave DRAFT with no lines, unpriced lines or missing totals; a sent/accepted quotation's lines cannot change.
- A price set by the AI agent is rejected unless an APPROVED `PROPOSE_PRICE` request, decided by the OWNER, for that quotation backs it. A price always records who set it.
- An issued invoice is immutable except status and e-invoice reference; its lines are frozen; its financial-year + serial number is unique; it cannot be issued without a number.
- An order's customer must match its quotation's; an invoice's must match its order's.
- `updatedAt` is maintained by the database as well as by Prisma.

## 4. Row Level Security policies

For **every** table in `public` (done by a loop, so `_prisma_migrations` is covered too):

1. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` - written out once per table (so it is visible, and the Supabase SQL Editor adds nothing of its own) and then again by the loop
2. `REVOKE ALL … FROM anon, authenticated` (Supabase's browser-facing roles)
3. `CREATE POLICY "deny_api_access" … AS RESTRICTIVE FOR ALL TO anon, authenticated USING (false) WITH CHECK (false)` — a restrictive policy, so even a permissive policy added later by mistake cannot open a table
4. `ALTER DEFAULT PRIVILEGES … REVOKE ALL … FROM anon, authenticated` so tables created later are not handed out either

Steps 2–4 run only where the `anon` / `authenticated` roles exist (Supabase); on plain PostgreSQL they are skipped.

**Tested** (against a database set up like Supabase, where those roles are granted everything by default): `anon` and `authenticated` get "permission denied" on reads and writes; and with `SELECT` deliberately re-granted, `anon` still sees **zero rows**.

## 5. Which tables are publicly readable

**None, through the Supabase API.** Nothing is readable by `anon` or `authenticated`.

The public website still shows the catalogue: the Next.js **server** reads `Category`, `Brand` (only `isListedPublicly`) and `Product` (only `ACTIVE`, public columns only) with its own database connection and renders HTML. Row-level security cannot hide *columns*, and `Product` holds purchase / wholesale / retail prices, so granting the API roles `SELECT` on it would leak them — that is why the API is closed entirely. If a browser-side catalogue is ever wanted, add a separate view with only public columns, not a policy on `Product`.

## 6. Which operations need admin access

There is no Supabase-user-level access at all. Every operation happens in the Next.js server, in one of two ways:

| Operation | Who / how |
| --- | --- |
| Show catalogue, brands, categories on the website | Anyone — server renders public columns of active rows |
| Submit a bulk-order / quote / contact form (creates `Lead`, `Enquiry`, `EnquiryItem`) | Anyone — server action: validated, honeypot, request-size limit; rate-limit still to add at Vercel |
| Everything else: create / edit / deactivate products, brands, categories; prices; stock; view enquiries, leads, customers; quotations; orders; invoices; payments; follow-ups; approvals; users | **Signed-in admin only** — `requireAdmin()` on every function (admin sign-in is not built yet, so the admin stays closed in production) |
| Approve an `ApprovalRequest` | **OWNER role only** (staff cannot — enforced by a CHECK and by `canExecute`) |
| Money movement, refunds, changing payment details | Never by the AI agent (policy), and payments cannot be deleted |

## 7. Security risks and assumptions

**Risks to know about**
1. **The app connects as the table owner (`postgres`), which bypasses RLS.** RLS here protects the Supabase *API*; it does nothing against a leaked `DATABASE_URL` or an injection bug. Prisma parameterises queries; before launch, create a least-privilege database role for the app (no DDL, no `TRUNCATE`) and use that in `DATABASE_URL`. I did not do this in the migration because it needs a password, which must never be in the repository.
2. **`SUPABASE_SERVICE_ROLE_KEY` bypasses all row security.** It is only for server-side Storage uploads. Never put it in the browser, in `NEXT_PUBLIC_*`, or in git. Mark it *Sensitive* in Vercel; rotate it if it ever leaks.
3. **Triggers protect against application / AI-agent mistakes, not against someone with full database access.** The Supabase SQL editor runs as the owner and can change anything (including disabling a trigger). Treat dashboard access as owner-level.
4. **Disable Supabase's Data API** (Project Settings → Data API) if you will not use it. It is closed by this migration anyway; turning it off removes the surface entirely.
5. **Personal data** (names, phones, e-mails of leads) will live in Supabase. Choose a nearby region (e.g. Mumbai), restrict dashboard access, and publish a privacy policy (India's DPDP Act).
6. **Storage buckets have their own policies** (`storage.objects`), not covered here. Plan: one bucket for product images, public *read* only (the images are public anyway), uploads only from the server with the service-role key, no policies for `anon`.

**Assumptions I made — tell me if any is wrong**
- Admin sign-in uses our own `AdminUser` + `AdminSession` tables (not Supabase Auth), so there is no link to `auth.users`. If you prefer Supabase Auth, that changes these two tables.
- Currency is INR only; money is `Decimal(12,2)`.
- `Lead`, `Customer` and `Enquiry` stay deletable (when nothing refers to them) so a personal-data erasure request can be honoured.
- A deleted admin user is only possible while they have decided no approval and recorded no payment; otherwise deactivate them (`isActive = false`).
- Pooled `DATABASE_URL` (Supabase pooler) for the running app on Vercel; `DIRECT_URL` (direct connection) only for migrations.
- The checks run on plain PostgreSQL 16 with `anon` / `authenticated` simulated. **Please apply the migration first to a new, empty Supabase project (staging) and run `npm run db:test-migration` against it** before touching the real one.

## How to run it, once approved

**Easiest, with no secrets shared:** follow [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md) — paste three SQL files into the Supabase SQL Editor. The steps below are the command-line alternative.

1. Create the Supabase project; copy `DATABASE_URL` (pooled), `DIRECT_URL` (direct), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` into Vercel → Settings → Environment Variables (and `.env.local` for local work). Never commit them.
2. With `DIRECT_URL` set in your shell: `npx prisma migrate deploy`.
3. `TEST_DATABASE_URL=<a throwaway database, NOT production> npm run db:test-migration`.
4. `npm run db:seed` (dry run) and then `npm run db:seed -- --apply` to load the owner-supplied categories, brands and the five products. Only after that set `CATALOGUE_SOURCE=database` in Vercel.
